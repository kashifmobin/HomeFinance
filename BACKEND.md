# Backend (Node.js + Express)

Our own API in front of PostgreSQL. No Supabase or other backend-as-a-service. Auth, authorization, audit and sync are code we own and test.

## Is this over-engineering?

**No, for this app.** It stores a family's financial history and children's data, so owning authentication, authorization and auditing is reasonable. What would be over-engineering is the extras people add around it. Rules to keep it proportionate:

- **One modular monolith**, one deployable, one Postgres. No microservices, Kubernetes, GraphQL, event sourcing or message brokers.
- **REST + JSON**, versioned (`/v1`).
- **Postgres-backed jobs** (pg-boss), no Redis until it is actually needed.
- **Managed Postgres** with automated backups, so we do not run the database ourselves.

Real costs to accept: roughly 3–5 extra weeks over Supabase (auth flows, sync API, authorization tests, deployment, backups, monitoring) and ongoing responsibility for security patches. The app does not move money and never stores bank credentials, so the risk is privacy of financial data, which this design addresses.

Each module: `routes.ts` (HTTP only) → `service.ts` (business rules, DB transactions) → `repo.ts` (queries) plus `schema.ts` (zod). No business logic in routes.

## API contract

The contract lives in `shared/openapi.yaml` at the repo root (see ARCHITECTURE.md). Update it before changing an endpoint. Backend tests check that every route matches the contract; the Flutter client is generated from it.

## Authentication

- Access token: JWT, **15 minutes**, contains `sub` (user id) and `sid` (session id). Signed with a rotating key.
- Refresh token: random opaque string, **stored hashed** in `refresh_tokens`, **rotated on every use**; reuse of an old token revokes the whole token family (theft detection).
- Mobile stores tokens in secure storage (Keychain / Keystore).
- OTP: 6 digits, expires in 5 minutes, hashed, limited attempts, resend throttled.
- Login throttling per IP and per account; lockout and notification on repeated failures.
- Sessions list and "log out everywhere" endpoints.
- **Managed child profiles have no credentials.** They are acted on by their parent's session. To give a teen or child their own login, the parent generates a one-time code; the child signs up and redeems it, which attaches the new user to the existing profile (history preserved).

## Authorization (replaces Row Level Security)

All permission logic lives in `src/authz/`. Nothing else decides who can see what.

- Every request resolves an **actor**: user → their profile → family memberships and roles.
- `can(actor, action, resource)` for single records, and `visibleProfileIds(actor)` / `scopeQuery(actor)` helpers so **list queries are filtered at the SQL level**, never post-filtered in JS.
- Rules follow the table in DATA_MODEL.md (private vs family entries, managed children, family goals and bills, roles owner/parent/adult/teen/child).
- Default deny: a route without an authorization check fails a test (a test enumerates all routes).
- A permission matrix test covers every role against every resource type (read, create, update, delete).
- Optional later: PostgreSQL RLS as a second layer, with the API setting the current profile per transaction.

## API design (`/v1`)

Conventions: JSON, ISO dates, amounts as **integers in minor units**, UUID ids generated by the client, `Idempotency-Key` header on non-sync POSTs, consistent error shape `{ error: { code, message, fields? } }`, cursor pagination.

## Sync API

- Every synced row carries `server_seq bigint`, assigned from a global sequence on every insert or update (trigger). Pull cursors use `server_seq`, **not** client timestamps, so clock skew cannot lose changes.
- `POST /sync/push` body: `{ deviceId, changes: [{ table, id, op: 'upsert'|'delete', baseVersion, data }] }`.
  - Processed in one DB transaction per batch; each change is validated with zod and authorized with `can()`.
  - Response: per-change result `applied | conflict | rejected(reason)` plus the server version for conflicts.
- `GET /sync/pull?cursor=<server_seq>&limit=500` returns changed rows the actor is allowed to see (scoped by authz), plus the new cursor and `hasMore`.
- Conflicts: last-write-wins on `updated_at` (clamped to server time) for most tables; the response lets the app show "changed on another device" for ledger rows. Balances are never synced; they are derived.
- Deletes are soft (`deleted_at`), returned in pull so other devices remove them.
- Idempotent by design: client-generated UUIDs make retries safe.
- Server enforces money invariants regardless of what the client sends: positive amounts, valid currency, transfer legs, goal contribution limits, ownership of referenced accounts and categories.

## Prisma notes

- **Custom SQL in migrations.** Create with `prisma migrate dev --create-only`, then add by hand what the schema file cannot express: partial unique indexes (e.g. `(account_id, external_ref) where external_ref is not null`), check constraints (`amount > 0`, transfer needs `to_account_id`), the global `server_seq` sequence and its trigger, and `citext`. Commit these migrations like any other.
- **Money is `BigInt`.** Prisma returns `bigint` for `BIGINT` columns, and `JSON.stringify` throws on it. Convert in one serializer (to a JSON number, which is safe for expected amounts, with an upper-bound check on input). Never scatter conversions through the code.
- **Soft deletes.** A Prisma client extension filters `deleted_at is null` by default; sync endpoints opt in to see deleted rows.
- **Authorization scoping.** Wrap queries in the authz helpers so every list query includes the visible-profile filter in the `where` clause.
- **Raw SQL for reports.** Group-by aggregates (by category, trend, saved/spent/given) use `$queryRaw` with parameters, covered by tests that compare results with the app's derived balances.
- **Enums.** Prisma enums map to the Postgres enums in DATA_MODEL.md; adding a value is a migration.
- **Tests** run Prisma against a real Postgres (Testcontainers needs Docker, so locally use a separate test database instead and keep Testcontainers for CI if wanted).

## Money correctness

- All amounts are `BIGINT` minor units end to end. JSON numbers stay within safe integer range for expected values; validate an upper bound.
- Multi-row operations (transfer, goal contribution, bill paid, allowance) run in a **single DB transaction**.
- Reports use SQL aggregates over non-deleted rows; derived balances come from the same queries the app uses, and the tests compare the two.

## Security checklist

- TLS only; HSTS; no secrets in the repo (env / secrets manager).
- Input validation everywhere; parameterized queries only.
- Rate limits on auth, OTP and sync endpoints; request size limits.
- Log redaction: never log tokens, OTPs, amounts with identity, note text or message text.
- `audit_log` rows for security-relevant events (login, token reuse, role change, invite, export, deletion, permission denials).
- Encryption at rest (managed disk/DB encryption); optional app-level encryption of free-text fields later.
- No card numbers, bank credentials or other-service passwords are ever accepted; `last4` is a label only.
- Backups: automated daily plus point-in-time recovery; **restore tested** before beta and then on a schedule.
- Dependency scanning (Dependabot / `npm audit`), pinned base image, non-root container.
- Account deletion and data export implemented (privacy). Review local data protection requirements before public launch.
- Security review and basic penetration test before beta.

## Hosting and operations

> **Deferred.** Deployment is decided later. Until then, run the API locally against a local PostgreSQL (Docker is not required). Keep the app 12-factor (config from environment, stateless) so any host works.

- Start simple: one container service (Render, Railway, Fly.io, DigitalOcean App Platform or a small VPS with Docker) plus managed PostgreSQL. Prefer hosting in Pakistan or with a cloud provider that complies with SBP's cloud framework: the draft Open Banking Regulations (October 2026) require customer data to stay in Pakistan, and the pending data-protection bill may require it for critical personal data (see MARKET_AND_DATA_CAPTURE.md).
- Environments: `dev` (local compose), `staging`, `prod`, each with its own database and secrets.
- Migrations run in CI/CD before the new version starts; they are backward compatible for one release so older app versions keep working.
- Health checks, uptime monitoring, error tracking (Sentry), and an alert on elevated 5xx or failed syncs.
- API versioning: `/v1` stays stable; mobile app sends its version and the API can require an upgrade.
